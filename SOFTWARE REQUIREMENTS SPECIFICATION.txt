1. INTRODUCTION

1.1 Purpose
This document specifies the software requirements for a Real-Time Sensor Data 
Processing System that continuously generates sensor data, processes it into 
blocks, calculates statistical parameters, and provides real-time monitoring 
via REST API and Server-Sent Events (SSE).

1.2 Scope
The system shall:
- Generate simulated sensor data with configurable error/missing rates
- Process data asynchronously using producer-consumer pattern
- Calculate six statistical parameters per data block
- Provide REST API endpoints for monitoring and control
- Stream real-time updates via Server-Sent Events
- Support runtime configuration changes
- Handle incomplete blocks via timeout mechanism

1.3 Definitions
- Block: A collection of sensor samples (default 100) processed together
- Valid sample: Integer between 0-100 inclusive
- Missing sample: None value (sensor failed to read)
- Corrupted sample: Value outside [0,100] or non-numeric error string
- SSE: Server-Sent Events for real-time streaming
- Timeout watchdog: Background task that flushes incomplete blocks after inactivity

2.1 Sensor Data Generation

-------------------------------------------------------------------------------
ID      | Requirement                                    | Priority
-------------------------------------------------------------------------------
FR-01   | System shall generate simulated sensor         | High
        | samples asynchronously                         |

        | [0, 100]                                       |
FR-03   | System shall support configurable missing      | Medium
        | data rate (default 2%)                         |
FR-04   | System shall support configurable error/       | Medium
        | corruption rate (default 5%)                   |
FR-05   | Missing samples shall be represented as None   | High
FR-06   | Corrupted samples shall be represented as      | High
        | error strings ("ERROR", "INVALID") or out-     |
        | of-range numbers (-1, 101)                     |
-------------------------------------------------------------------------------

2.2 Data Processing

-------------------------------------------------------------------------------
ID      | Requirement                                    | Priority
-------------------------------------------------------------------------------
FR-07   | System shall process data into blocks of       | High
        | configurable size (default 100)                |
FR-08   | System shall use asynchronous producer-        | High
        | consumer pattern for processing                |
FR-09   | System shall maintain bounded queue            | High
        | (default 1000) between producer and consumer   |
FR-10   | System shall detect and count queue overflow   | Medium
        | events                                         |
FR-11   | System shall support runtime block size        | High
        | changes without restart                        |
FR-12   | When decreasing block size, system shall       | Medium
        | split current block into smaller blocks        |
FR-13   | When increasing block size, system shall       | Medium
        | continue accumulating current block            |
FR-14   | System shall support force-processing current  | Medium
        | block before size change                       |
-------------------------------------------------------------------------------

2.3 Statistical Calculations (Part a)

-------------------------------------------------------------------------------
ID      | Requirement                                    | Priority
-------------------------------------------------------------------------------
FR-15   | System shall calculate maximum value from      | High
        | valid samples                                  |
FR-16   | System shall calculate minimum value from      | High
        | valid samples                                  |
FR-17   | System shall calculate mean (average) from     | High
        | valid samples                                  |
FR-18   | System shall calculate sample standard         | High
        | deviation using Bessel's correction (N-1)      |
FR-19   | System shall count missing samples             | High
        | (None values)                                  |
FR-20   | System shall count corrupted samples           | High
        | (invalid values)                               |
FR-21   | System shall return None for statistics when   | Medium
        | no valid samples exist                         |
FR-22   | System shall return 0.0 for standard          | Low
        | deviation when only 1 valid sample exists      |
-------------------------------------------------------------------------------

6. ACCEPTANCE CRITERIA

The system is considered complete when:

AC-01: System starts successfully and shows startup banner
AC-02: Sensor data generation produces mixed valid/missing/corrupted samples
AC-03: Blocks are processed with correct statistics (validated N-1 std deviation)
AC-04: Formatted output appears after each block
AC-05: All API endpoints return expected responses
AC-06: SSE stream sends updates when blocks complete
AC-07: Block size can be changed at runtime without restart
AC-08: Timeout watchdog flushes incomplete blocks after inactivity
AC-09: Queue overflow does not crash system
AC-10: System can be stopped and started via API
AC-11: Reset clears all state correctly

8. GLOSSARY

Bessel's correction  : Use of N-1 instead of N when calculating sample variance
Producer-consumer    : Pattern where one task produces data and another consumes it
Queue overflow       : When queue is full and new data cannot be added
Server-Sent Events   : HTTP streaming protocol for real-time updates
Watchdog             : Background task monitoring system health
Asyncio              : Python's asynchronous I/O framework
